# DEX-1012 editor association demo

This self-contained fixture demonstrates schema association for Rudder YAML files
whose names and directories are arbitrary. The root and event-stream-source
schemas in `schemas/` were generated by `rudder-cli schema --out` from
rudder-iac PR #927 at commit `bbcee89`. They are spike evidence from an open PR,
not a published schema contract.

The automated result is checked in at
[`evidence/yaml-language-server-matrix.json`](evidence/yaml-language-server-matrix.json).
The run used yaml-language-server 1.24.0 and directly exercised the sample
modelines, relative schema paths, and a `yaml.schemas`-equivalent association.

**VS Code UI proof status:** incomplete. A browser-installable VS Code binary was
unavailable in the build environment. The headless matrix proves
yaml-language-server behavior only; before Part 2 ships, record a real VS Code
screenshot/GIF or screencast with the Red Hat YAML extension and the version
numbers used.

## What is included

- `samples/sources/mobile.yaml`: arbitrary path/name associated by the generated
  per-kind modeline recommended for importer/scaffolding output.
- `samples/root-comparison/mobile.yaml` and `customer-360.yaml`: source and
  data-graph documents associated with the root through `.vscode/settings.json`
  solely to compare discriminator behavior.
- `samples/settings-associated.yaml`: no modeline; `.vscode/settings.json`
  associates this exact arbitrary filename through `yaml.schemas`.
- `schemas/rudder-spec.schema.json`: PR #927's Draft 2020-12 root with 14
  constant-`kind` `oneOf` branches.
- `schemas/event-stream-source.schema.json`: the generated per-kind schema used
  for the direct-association comparison.
- `verify.mjs`: the executable completion, hover, and validation matrix.

## Manual VS Code proof still required

These steps are the remaining acceptance check to run in a desktop VS Code
session; they are not completed by the checked-in headless matrix.

1. Open this `docs/spikes/DEX-1012/demo` directory as the workspace.
2. Install the recommended `redhat.vscode-yaml` extension.
3. Open `samples/sources/mobile.yaml`.
4. Remove a key below `spec:`, place the cursor at that indentation, and invoke
   **Trigger Suggest**. The expected source fields (`id`, `name`, `type`, and
   `enabled`) are offered and data-graph fields are not.
5. Hover `enabled`: the hover identifies the selected RudderStack
   event-stream-source schema and its schema source.
6. Open `samples/root-comparison/mobile.yaml`, then change `kind` to
   `data-graph`. Source keys become invalid and completion switches to `id`,
   `account_id`, and `models` through the root mapping.
7. Open `samples/settings-associated.yaml` to verify direct per-kind association
   without a modeline.

## Re-run the headless matrix

The checker uses the same `yaml-language-server` package embedded by Red Hat
YAML. Dependencies are intentionally not vendored into this docs-only spike.

```sh
mkdir -p /tmp/dex-1012-yls
npm install --prefix /tmp/dex-1012-yls \
  yaml-language-server@1.24.0 \
  vscode-languageserver-textdocument@1.0.15
node verify.mjs
```

Set `DEX_1012_YLS_ROOT` to use a dependency directory other than
`/tmp/dex-1012-yls`.

## Recorded result: root versus per-kind

The generated root validates and narrows correctly after `kind` is present, but
its completion before `kind` is noisy. At `spec:` with no discriminator,
yaml-language-server offers fields from multiple branches (including source
`enabled` and graph `account_id`). After `kind: event-stream-source`, it offers
source fields and excludes graph fields. The generated per-kind schema is
focused in both states, which is why importer/scaffolding modelines should use
`<kind>.schema.json`; the root remains useful for SchemaStore and project globs.

The assertions cover:

| Schema | State | Expected result |
| --- | --- | --- |
| Root mapping and source per-kind modeline | blank document | envelope completion (`version`, `kind`, `metadata`, `spec`) |
| Root mapping and source per-kind modeline | after `version`, before `kind` | `kind`, `metadata`, and `spec` completion |
| Root `yaml.schemas` mapping | `kind: event-stream-source` | source fields included; graph fields excluded below `spec` |
| Root `yaml.schemas` mapping | `kind: data-graph` | graph fields included; source fields excluded below `spec` |
| Per-kind modeline | event stream source | source completion and hover below `spec` |
| `yaml.schemas` equivalent | event stream source | source completion without a modeline |
| Root `yaml.schemas` mapping | inside `spec`, before `kind` | mixed cross-kind suggestions and a missing-kind diagnostic |
| Root `yaml.schemas` mapping | kind changed but source fields remain | wrong-kind and missing graph-field diagnostics |
| Root `yaml.schemas` mapping | hover on `spec.enabled` | selected schema title and source link |

The checked-in matrix output is evidence, not a replacement for the manual VS
Code steps. It makes the behavior reproducible even when a desktop session is
not available.
